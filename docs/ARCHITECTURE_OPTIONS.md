# Упрощение инфраструктуры — обсуждение

28 октября 2026. Статус: варианты, решение о миграции не принято.

## Ограничения

Домашняя игра с дочкой, несколько телефонов и Android TV. Бесплатная эксплуатация, без включённого ноутбука. Текущие Cloudflare/Supabase медленно работают у пользователя; Cloudflare бывает недоступен. Причина задержек измерениями пока не установлена. Доступность других провайдеров из домашней сети не проверялась.

## Общая архитектура независимо от размещения

Сохранить Vue-интерфейс и единый TypeScript-движок. Небольшой авторитетный сервер принимает команды, проверяет участника, применяет движок, сохраняет состояние и возвращает разрешённый снимок. Клиенты не записывают произвольный JSON напрямую.

Для такого масштаба достаточно таблицы `rooms`: `id`, `code` (unique), `revision`, `document_json`, `updated_at`. JSON содержит schemaVersion, roomId, matchId, rulesVersion, leaderPlayerId, участников с хешами токенов восстановления, публичное состояние, приватные руки и принятые идентификаторы команд. Новая партия меняет matchId, сохраняя комнату и места. Архив партий — необязательное последующее расширение.

Запись должна быть атомарной: прочитать версию → проверить команду → вычислить результат → сохранить при совпадении revision. При конфликте перечитать и повторно проверить команду. Подтверждать ход только после сохранения. Дубликат commandId возвращает прежний результат, а команда старого matchId отклоняется. Случайный результат обмена фиксируется вместе с командой. Для каждого игрока сервер формирует публичный снимок + только его приватную руку; токены и полная колода не публикуются.

На первом этапе достаточно HTTP-команд и опроса версии примерно раз в секунду при активной игре; интервал измерить на устройствах. Нужны запрет параллельного sync, повтор после возврата телефона, сохранение черновиков. SSE/WebSocket можно добавить, если задержка раскрытия окажется заметной. При облачном размещении частота опроса должна укладываться в лимиты провайдера.

Слой доступа клиента: create/open, join/resume, snapshot, command. Текущие Supabase-вызовы из store заменить через адаптер, не смешивая перенос сервера с редизайном и изменением правил.

## Вариант A: облако, наиболее прямой перенос текущего кода

Один Node.js-сервис раздаёт Vue-сборку и API с одного origin. Например, бесплатный Koyeb во Франкфурте плюс постоянная БД Turso; Render — альтернативный хост. JSON хранить в одной строке БД, доступ к БД только с сервера. Подтвердить транзакционную семантику выбранного драйвера до реализации.

- Koyeb Free: один экземпляр, 512 МБ RAM, 0.1 vCPU, Frankfurt/Washington, сон после часа без трафика, без постоянного volume. [Условия](https://www.koyeb.com/docs/reference/instances).
- Render Free: сон после 15 минут, пробуждение около минуты, локальная SQLite теряется при рестарте/сне, бесплатный Postgres истекает через 30 дней. [Условия](https://render.com/docs/free).
- Turso имеет бесплатный тариф для постоянной БД. [Тариф](https://turso.tech/pricing?frequency=monthly). Лимиты и возможность регистрации повторно проверить перед развёртыванием.
- Oracle Always Free допускает свой сервер с диском, но простаивающие машины могут быть отозваны, возможен дефицит ресурсов и требуется проверка регистрации. Для редкой игры это не основной выбор. [Ограничения](https://docs.oracle.com/en-us/iaas/Content/FreeTier/freetier_topic-Always_Free_Resources.htm).

Преимущество: можно сохранить TypeScript на сервере и существующий клиент, обновлять сайт без APK после первоначальной смены адреса. Компромисс: два внешних сервиса, холодный старт, зависимость от маршрута и доступности провайдеров. Бесплатный тариф не гарантирует отсутствие блокировок. До переноса проверить адрес кандидата с телефона и ТВ: загрузку, пробуждение, запросы и восстановление.

## Вариант B: телевизор как домашний сервер

APK включает веб-сборку, локальный HTTP-сервер и SQLite в приватном каталоге Android. Телефоны открывают адрес ТВ из QR; телевизор показывает общую доску. Всё работает в одной домашней сети без облака. Android поддерживает локальные сетевые взаимодействия и SQLite: [локальная сеть](https://developer.android.com/develop/connectivity/wifi), [хранение](https://developer.android.com/training/data-storage/sqlite).

Это кандидат для полностью бесплатной автономной игры, но не готовая возможность текущего приложения. Нужен небольшой технический прототип перед подробным заданием на перенос.

Проверить прототипом:

1. ТВ принимает HTTP-запросы с двух телефонов по домашней сети; нет изоляции Wi-Fi-клиентов. QR содержит актуальный LAN-адрес и порт.
2. APK раздаёт все ресурсы локально; отключение интернета не мешает началу партии.
3. Выбрать среду исполнения общего TS/JS-движка на Android и проверить совместимость, размер и интеграцию сборки. Node.js внутри Android сейчас отсутствует. Не дублировать правила на Java без необходимости. WebView как вычислительный мост потребует отдельной проверки сериализации команд и жизненного цикла.
4. Сохранение JSON переживает закрытие приложения; при завершении процесса клиенты видят потерю связи и восстанавливаются после запуска. Сервер нужен только пока игровое приложение открыто.
5. Продумать локальный HTTP: в APK сейчас разрешён только фиксированный HTTPS-домен и запрещён cleartext. Изменить сетевую политику и проверку адресов целенаправленно, не открывать произвольную навигацию. [Android network policy](https://developer.android.com/privacy-and-security/security-config).
6. На LAN HTTP нет гарантий secure context: текущий `crypto.randomUUID()` требует замены/совместимого подхода; HTTPS-зависимые функции проверять отдельно. [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID). Не рассчитывать на PWA/service worker.
7. При смене IP меняется origin и доступ к браузерному хранилищу: нужен стабильный адрес (например, DHCP reservation) либо процедура повторной привязки. Простой QR решает поиск сервера, но сам по себе не переносит авторизацию между origin.

Компромиссы: первоначальная Android-разработка сложнее облачного переноса, обновления веб-сборки входят в APK, игра доступна только в этой сети при включённом приложении. Домашний HTTP не предназначен для публичной/гостевой сети; не требуется открывать порт в интернет.

## Что решаем следующим

Сначала выбрать компромисс: проще обновлять через бесплатное облако с возможным ожиданием первого запуска или вложиться в автономный ТВ-режим. Затем составить ограниченное задание: для облака — проверка доступности и маленький API; для ТВ — прототип сети, исполнения движка и сохранения. Полную миграцию начинать после успешной проверки выбранного пути.

## Работа через коммиты

1. Обсуждаем поведение и архитектурное решение здесь.
2. Готовим задание кодировщику: цель, что сохраняется, границы, модель данных/API, ошибки и гонки, изменения по файлам, критерии приёмки и проверки.
3. Кодировщик работает в отдельной ветке, делает небольшие осмысленные коммиты и сообщает SHA, результаты тестов и ограничения.
4. Ревью сравнивает изменения с согласованным базовым коммитом: корректность, приватность, повторные запросы, восстановление, UX и регрессии.
5. Замечания сопровождаются сценарием воспроизведения и ожидаемым результатом; исправления — следующими коммитами. Изменения принимаются после проверки. Merge в main запускает действующую автопубликацию; экспериментальный перенос инфраструктуры до приёмки вести в отдельной ветке.
