# Постоянная доска: согласованное изменение

Статус: операции доски, секрет устройства, ID партии и интерфейс реализованы в рабочей копии. Они используют существующие таблицы и новую миграцию; переход на три основные таблицы пока не выполнен. 28 октября 2026 SQL миграции и операции создания и восстановления доски, смены кода, сброса, восстановления после сброса и проверки неверного секрета проверены на рабочей базе внутри транзакции с откатом; отдельно подтверждено, что схема откатилась. Полный сценарий через Edge Functions и несколько устройств ещё не проверен. Миграция не применена, функции и клиент не опубликованы. Действующую опубликованную схему см. в SUPABASE_SETUP.md.

## Поведение

- Доска на ТВ постоянно принадлежит устройству. Код подключения остаётся прежним между партиями и перезапусками. Его можно обновить в настройках ТВ, не меняя состав и текущую партию; старый код перестаёт работать.
- Доска, её участники и партия — отдельные сущности. Первый вошедший участник становится лидером; при одновременном входе назначение выполняется атомарно. Лидер управляет партией.
- «Играть снова» создаёт новую партию на той же доске, сохраняя участников, лидера и код. У каждой партии свой ID.
- «Сбросить доску» доступен на ТВ после подтверждения. Текущая незавершённая партия прекращается без результата, участники отключаются; создаётся новая доска с новым ID и кодом. Старая доска больше не принимает вход и действия. Первый участник новой доски становится лидером.
- Данные ТВ: ID доски и случайный секрет в локальном хранилище приложения; сервер хранит только хеш секрета. После перезапуска сервер проверяет секрет и возвращает прежнюю доску. Утеря данных устройства означает новую доску. При сетевой ошибке существующую привязку не удалять и новую доску не создавать.
- Игрок восстанавливает своё место по сохранённой анонимной авторизации; сервер возвращает актуальную партию и разрешённые личные данные. После сброса доски старое место больше не восстанавливается. Существующий черновик привязан к ID доски, ID партии, ID игрока и раунду.
- До отправки хода можно возвращаться к торговле, в том числе после обмена; карта и использованный обмен сохраняются.

## Модель и доступ

Три основные сущности: `boards` (ID, код, хеш секрета, статус, версия), `board_players` (ID доски, игрок, связанный пользователь, имя, лидерство) и `matches` (ID, ID доски, версия, состояние партии и приватные данные игроков в JSON). Точные названия — часть реализации. Должны обеспечиваться уникальность активного кода, не более одного лидера и одной активной партии на доску. Необязательные вспомогательные таблицы допустимы, если они нужны для безопасной синхронизации или миграции.

Полный JSON закрыт от прямого чтения клиентов. Сервер проверяет авторизацию и членство и возвращает каждому игроку публичное состояние и только его личные данные; ТВ получает публичное состояние. Код доски и имя игрока не служат подтверждением личности. Действия применяются сервером и сохраняются атомарно с проверкой версии, ID партии и ID хода; повторная отправка не применяется дважды. При последнем ходе все результаты раскрываются атомарно. Клиент не получает полную колоду.

## Переход и проверка

1. Уточнить сопоставление текущих `game_hubs`, `game_sessions`, `game_seats` и приватных данных с новой моделью; сохранить существующий код и участников активной доски. Для ранее созданной доски зарегистрировать секрет на устройстве через уже авторизованную сессию; не передавать и не записывать секрет в журналы.
2. Добавить миграцию без удаления действующих таблиц, серверные операции и проверку прав. Переносить существующие данные транзакционно и сохранить возможность отката. Удалять старые таблицы только после проверки совместимости и успешного переноса.
3. Добавить на ТВ настройки обновления кода и подтверждённого сброса; добавить новую партию с прежним составом. Не смешивать сброс доски со сменой кода.
4. Перевести восстановление и черновики на идентификаторы доски и партии. Различать временную недоступность и подтверждённое удаление/отзыв доступа. QR прежнего кода и открытая вкладка после сброса не восстанавливают прежнее место.
5. Проверить на реальной тестовой БД и нескольких устройствах одновременный вход, смену кода, сброс во всех фазах, повторную партию, потерю связи и ответа на отправку, перезапуск ТВ и телефонов, доступ к чужим картам, старые запросы и черновики. Затем проверить миграцию и откат до выпуска.
