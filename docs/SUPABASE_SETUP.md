# Сервер Supabase

Справочник текущей реализации. Адреса проекта, история применённых миграций, secrets, локальный запуск и порядок обновления собраны в [DEPLOYMENT.md](DEPLOYMENT.md). Для обычного выпуска использовать GitHub Actions.

## Авторизация и доступ

Anonymous sign-ins включён: у каждого браузера своя Supabase-сессия, её пользователь определяет место игрока. Выбранное имя и код комнаты не заменяют авторизацию.

В `supabase/config.toml` у `create-room`, `join-room`, `game-action` установлено `verify_jwt = false`. Это отключает legacy-проверку JWT на шлюзе. Обработчики сами проверяют токен через `auth.getUser(token)` и полномочия на комнату перед выполнением действия.

Все игровые таблицы защищены RLS. Клиент читает доступную ему публичную сессию и места; закрытые таблицы не имеют клиентских политик чтения. Supabase предоставляет функциям `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Служебный ключ остаётся на сервере и не включается в клиентские `VITE_*`.

## Таблицы

| Таблица | Содержимое и ограничения |
| --- | --- |
| `game_sessions` | Публичное состояние, код, лидер, версия и статус комнаты; Realtime включён для этой таблицы |
| `game_seats` | Связь Supabase-пользователя с местом игрока |
| `game_viewers` | Пользователи с доступом к доске |
| `game_player_private` | Рука, колода, сброс, счётчик обменов, ожидающий ход и ID отправки; браузер напрямую не читает |
| `game_hubs` | Владелец доски/хаба, активная комната, режим `display` или совместимый `key`, хеши ключей |
| `game_influence_choices` | Наследие первого сетевого прототипа; текущий протокол не использует |

`schemaVersion: 3` — текущая версия игровых данных. Полной серверной истории раундов нет: публичный снимок содержит последнее раскрытие. Клиент получает собственную разрешённую приватную часть, без колоды, сброса и чужих ожидающих ходов. Лидер не имеет доступа к чужим закрытым картам.

## Edge Functions и RPC

| Функция | Назначение |
| --- | --- |
| `create-room` | Открытие и восстановление доски, совместимость с хабами по ключу |
| `join-room` | Подключение игрока или дополнительной доски |
| `game-action` | Синхронизация, отправка хода, обмен карты, управление партией |

Исходники — `supabase/functions/<имя>/index.ts`. Общие модули: `_shared/game.ts` (движок), `_shared/api.ts` (Auth/чтение), `_shared/hubKey.ts` (ключи). Клиентский предпросмотр и тесты используют тот же движок. CLI упаковывает относительные импорты; вручную объединять обработчики в Dashboard для обычного выпуска не нужно.

`commit_v3_game` под блокировкой строки проверяет версию и управляющего и сохраняет публичное состояние, приватные данные и изменения мест атомарно. Устаревшая версия возвращает пустой результат: обработчик перечитывает состояние и повторяет действие. `read_v3_game` возвращает согласованный снимок с собственной рукой и ожидающим ходом. Прямое выполнение этих процедур разрешено только `service_role`.

Покупки, продажи, этап и выбор карты до отправки меняют локальный черновик. `submit-turn` передаёт `{round, id, trades: [{companyId, action}], cardId}`. Сервер повторно проверяет ход, защищает от дублей и хранит его приватно до общей готовности. Последняя отправка атомарно применяет все ходы и раскрывает карты. `exchange-card` — отдельный запрос `{round, cardId, selectedCardId}`; будущая колода в браузер не передаётся. Старые отдельные действия `buy`/`sell`/`finish-turn` больше не принимаются.

## Доски и совместимость

Текущий пользовательский сценарий описан в [GAME_RULES.md](GAME_RULES.md): доска создаёт лобби, первый игрок становится лидером.

`open_display_lobby` идемпотентно создаёт/восстанавливает активную комнату одного владельца доски. У `game_hubs.mode` значение `display`; `host_user_id` может быть NULL до входа первого игрока. `commit_v3_game` назначает его лидером под той же блокировкой, что и добавление места. `restart_display_lobby` проверяет лидера, закрывает прежнюю комнату и создаёт следующую; доска переключается на неё.

Старый сценарий `key` сохранён на сервере для совместимости, но больше не предлагается новым интерфейсом. `connect_game_hub` назначает единственного управляющего и отзывает управление у предыдущего подключения; `create_hub_room` создаёт комнату, место и приватные данные в транзакции. Ключи хранятся в базе только в виде хешей. После миграции `short_hub_keys` старый длинный ключ может преобразовываться в короткий; резервный `legacy_key_hash` сохраняет совместимость. Генерация и нормализация — в `_shared/hubKey.ts`.

## Новый пустой Supabase-проект

Это отдельная установка, а не повторная настройка текущей базы.

1. Создать проект и включить Anonymous sign-ins.
2. Авторизовать CLI в аккаунте с доступом к нему. Из корня репозитория выполнить команды ниже, заменив `NEW_PROJECT_REF` новым ref.
3. Опубликовать три функции с настройками `supabase/config.toml`.
4. Проверить RLS, доступ к своей комнате, запрет чтения чужих карт и наличие `game_sessions` в `supabase_realtime`.
5. Обновить URL/Publishable key в `.env.local`, а для автоматического выпуска — secrets и variables GitHub по [DEPLOYMENT.md](DEPLOYMENT.md). Сначала держать `DEPLOY_ENABLED=false` и `MIGRATION_BASELINE_VERIFIED=false`; включить после сверки и dry-run.

```sh
npx supabase login
npx supabase link --project-ref NEW_PROJECT_REF
npx supabase db push --linked --dry-run
npx supabase db push --linked
npx supabase functions deploy --project-ref NEW_PROJECT_REF
npx supabase migration list
npx supabase db push --linked --dry-run
```

К новой пустой базе применяются **все** файлы `supabase/migrations/` по порядку, включая будущие добавления. После применения dry-run должен показать отсутствие новых миграций. В отличие от существующей базы, здесь нет ранее выполненного вручную SQL, поэтому предварительный `migration repair` не нужен.

Данные партий и анонимные пользователи между проектами сами не переносятся. Диагностический URL Supabase в `MainActivity.java` также привязан к текущему проекту; при переносе backend обновить его при следующей сборке оболочки. Проверки на временной БД в Actions не подтверждают перенос реальных данных или восстановление резервной копии.
